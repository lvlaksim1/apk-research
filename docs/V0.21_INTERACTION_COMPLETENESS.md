# v0.21 — Interaction Completeness

## Purpose

Complete the existing Emulator gRPC interaction layer without replacing its proven transport.

## Gesture model

The embedded Android view supports:

- normal left drag: one-pointer touch/swipe;
- Ctrl+drag: two pointers symmetric through the display center, suitable for pinch/rotate;
- Shift+drag: horizontal mirror of the second pointer, suitable for vertical tilt;
- Ctrl+Shift+drag: vertical mirror of the second pointer, suitable for horizontal tilt.

Both pointers are transmitted in the same Emulator `TouchEvent` with identifiers 0 and 1.

## Geometry invariant

Every gesture starts on one display-geometry generation. A generation is defined by framebuffer width/height, Android input width/height and rotation.

Repeated frames with the same geometry keep the same generation. Any geometry change creates a new generation.

If geometry changes while a gesture is active, the old gesture is terminated using its last known points and no subsequent movement from that gesture is remapped onto the new geometry.

## Evidence

Completed two-pointer interactions are recorded as one `multi_touch` user action. Evidence includes mode, pointer count, start/end points, duration, maximum pointer displacement, geometry generation and completion state.

A geometry-interrupted single-pointer gesture is recorded as `gesture_cancelled` with `cancel_reason=display_geometry_changed`.

This evidence describes injected input only. It does not prove that the application consumed the gesture or that later network/process activity was caused by it.

## Unchanged boundaries

The release does not change:

- hidden Emulator → gRPC/MMAP → AndroidView presentation;
- persistent gRPC input transport;
- v0.10.5 startup and clean-launch sequencing;
- Research ZIP raw/derived authority model;
- Android sidecar responsibilities;
- continuous-screen A/B collector;
- Action ↔ Flow temporal-only semantics.
