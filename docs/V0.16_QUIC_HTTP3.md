# v0.16 — QUIC / HTTP/3 Network Intelligence

> **v0.16.1 correction:** a real v0.16.0 archive showed that arbitrary UDP payloads could accidentally match the long-header shape. Starting with v0.16.1, unknown versions are not asserted as QUIC, and v1/v2 flow context is established only after successful Initial authentication/decryption. Version Negotiation and later packets require that confirmed context.

## Purpose

v0.16 extends apk-research network analysis from TCP/TLS and generic UDP flows to explicit QUIC protocol evidence while preserving the RAW-first forensic model.

## Supported protocol evidence

The post-capture parser recognizes QUIC long headers and supports the standardized Initial protection for:

- QUIC v1, wire version `0x00000001`;
- QUIC v2, wire version `0x6b3343cf`.

For a client Initial, apk-research derives Initial secrets from the version-specific public salt and the client's initial Destination Connection ID, removes header protection, authenticates/decrypts the Initial payload, reads CRYPTO frames and reassembles contiguous TLS handshake bytes.

When a complete TLS ClientHello is available, the parser records:

- SNI;
- ALPN values;
- QUIC version;
- observed QUIC packet type;
- whether Initial decryption/authentication succeeded.

ALPN values `h3` and `h3-*` are classified as HTTP/3 evidence.

## Evidence semantics

QUIC detection is evidence-driven. A UDP flow is not labelled QUIC merely because port 443 is present or because arbitrary bytes resemble a long header. For supported v1/v2, a flow becomes confirmed only after successful Initial authentication/decryption; subsequent QUIC packet types may then reuse that established context.

QUIC Initial protection is intentionally derivable by passive observers under the protocol specification. Decoding it is not MITM and does not expose Handshake or 1-RTT traffic. apk-research therefore does not claim to decrypt HTTP/3 request/response content.

The existing TCP/TLS SNI path is unchanged. QUIC SNI is stored explicitly and is also made available to the existing host/timeline name path because it originates from the TLS ClientHello carried in QUIC CRYPTO frames.

## network-flows.json schema 0.3

The normalized flow record keeps the same canonical bidirectional 5-tuple identity and adds:

- `application_protocols`;
- `quic_versions`;
- `quic_packet_types`;
- `quic_sni`;
- `quic_alpn`;
- `quic_initial_decrypted`.

The summary adds:

- `quic_flow_count`;
- `http3_flow_count`;
- `quic_initial_decrypted_flow_count`.

These fields are derived evidence only. `01_raw/network/traffic.pcap` remains the source of truth.

## Network Analyzer

Host resolution prefers direct QUIC SNI evidence before the existing TLS SNI / DNS / remote-IP fallback. Search includes QUIC SNI, ALPN, version and application protocol. Flow details expose a separate QUIC / HTTP/3 section.

## Validation

Regression tests use the published RFC 9001 QUIC v1 and RFC 9369 QUIC v2 Initial derivation vectors and protected synthetic v1/v2 Client Initial packets containing SNI and HTTP/3 ALPN.

The real Research ZIP used to validate v0.13-v0.14 contains UDP traffic but no UDP/443 flow, so it does not provide a real QUIC session for this release. This limitation is recorded rather than inferred away.

## Unchanged boundaries

v0.16 does not alter:

- Android Emulator startup or clean-launch sequencing;
- gRPC/MMAP display and input transport;
- tcpdump raw capture;
- socket/PID/inode package attribution;
- canonical flow IDs;
- Timeline temporal-only correlation semantics;
- Research ZIP RAW evidence.
