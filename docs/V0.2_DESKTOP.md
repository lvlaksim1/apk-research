# Mobile Research — Desktop Application Contract

## Цель

Desktop-слой превращает Research Session Core в самостоятельное Windows-приложение. Штатный пользовательский сценарий не требует Python, PowerShell, Android Studio, ручного ADB или ручного создания AVD.

## Пользовательский сценарий

Установить `MobileResearchSetup.exe` → запустить Mobile Research → выбрать APK → программа сама готовит Android → работать с Android внутри окна → НАЧАТЬ ИССЛЕДОВАНИЕ → ЗАВЕРШИТЬ И СОХРАНИТЬ → Research ZIP.

## Self-contained Windows distribution

Python runtime и Qt входят в приложение. Пользователь не устанавливает Python, pip или venv.

## Managed Android components

Android Studio не требуется. Mobile Research загружает официальные Android packages из Google repository metadata в `%LOCALAPPDATA%\MobileResearch\components`.

Текущий baseline: platform-tools/ADB, stable Android Emulator из Google repository channel-0, build-tools 35.0.0/aapt2, Android 15 API 35 AOSP default x86_64 image и private AVD `mobile_research_api35`.

При первом использовании GUI получает одноразовое согласие с Android SDK License Agreement. После этого download, checksum verification, extraction и configuration выполняются программой.

## Embedded Android — active contract

Нормальный Windows display path не создаёт пользовательское standalone-окно Android Emulator.

Основная цепочка:

```text
emulator -qt-hide-window
        ↓
Emulator gRPC streamScreenshot
        ↓
MMAP/shared-memory framebuffer
        ↓
AndroidView
```

Если MMAP недоступен, используется gRPC byte-stream, затем ADB screenshot как последний framebuffer fallback.

Input независим от display transport: mouse/keyboard передаются через постоянный Emulator gRPC `streamInputEvent`. Pointer drag отправляется как настоящий DOWN → MOVE → UP lifecycle.

Порядок Windows compatibility profiles:

1. embedded gRPC/MMAP + GPU host;
2. embedded gRPC/MMAP + GPU auto;
3. headless SwiftShader;
4. DWM live + GPU host;
5. DWM live + GPU auto.

DWM является только последним compatibility fallback и не участвует в штатном запуске.

## Boot recovery

Graphics/display fallback применяется только к ошибкам запуска Emulator или графического backend.

Если процесс Emulator жив, но Android не достигает `sys.boot_completed=1`, это классифицируется как guest/AVD boot stall. Для такого случая допускается ровно одно автоматическое восстановление того же профиля через официальный `-wipe-data`.

Soft restart не используется. Если чистый AVD также не загружается, Mobile Research останавливается с ошибкой и не начинает новые длинные boot-циклы на следующих graphics profiles.

## Virtualization

Mobile Research проверяет Android Emulator acceleration. На Windows предпочтительный provider — WHPX. Уже установленный usable AEHD/GVM допускается как compatibility fallback и сам по себе не должен провоцировать UAC или блокировать запуск.

Если usable hypervisor отсутствует, Mobile Research одним UAC-запросом включает Windows Hypervisor Platform (`HypervisorPlatform`) и выставляет `hypervisorlaunchtype=Auto`. `VirtualMachinePlatform` автоматически не включается. Если требуется reboot, приложение сообщает об этом явно.

## Research core

Гарантии v0.1.0 сохраняются: immutable raw evidence, metadata, logcat, screen recording, mandatory raw PCAP, complete/partial/failed semantics, SHA-256 Research ZIP и semantic audit. GUI вызывает core classes напрямую и не запускает CLI subprocess.

## Build and release gates

Каждый релевантный commit запускает:

- `CI` на Windows;
- `AVD Research Acceptance` на реальном Linux/KVM Emulator;
- `Desktop Build` с тестами, standalone EXE, Inno Setup, installed-app smoke test и clean-Windows provisioning.

Stable Release workflow ждёт успешные `CI`, `AVD Research Acceptance` и `Desktop Build` для exact commit SHA и публикует проверенный `MobileResearchSetup.exe` из Desktop Build.

`Windows WHPX Acceptance` остаётся отдельной hardware-проверкой на dedicated Windows x64 runner. Пока этот runner не является гарантированно доступной частью CI-инфраструктуры, workflow считается advisory и не блокирует публикацию stable release. Его результат используется как дополнительное подтверждение реального WHPX path.

## Stable runtime baseline

Начиная с v0.8.4 active GUI/display code больше не содержит rejected SetParent/native-HWND embedding path. DWM fallback изолирован в `dwm_emulator.py`; primary framebuffer path остаётся независимым.

Начиная с v0.8.2 реальным пользовательским тестом подтверждены:

- отсутствие standalone Emulator flash;
- правильная ориентация gRPC/MMAP framebuffer;
- соответствие display и touch coordinates;
- плавный потоковый swipe;
- нормальный отклик embedded Android.

Дальнейшие изменения display/input runtime должны сохранять этот baseline и вноситься только при наличии конкретной воспроизводимой проблемы.
