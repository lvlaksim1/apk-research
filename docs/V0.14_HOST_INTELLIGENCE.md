# Mobile Research v0.14 — Host Intelligence: Service vs DNS

## Goal

Refine the host-first investigation model without modifying captured or normalized forensic evidence.

## Problem observed in real v0.13.0 evidence

A hostname group can legitimately contain two different flow roles:

1. a DNS query to a resolver, where the query name identifies the host group;
2. one or more service connections whose TLS SNI or DNS-derived identity identifies the same host.

Treating all remote endpoints and ownership values as equivalent makes the resolver look like a service server and can mix Unknown resolver attribution into otherwise proven app-owned service traffic.

## Derived role model

A flow is classified as dns-resolution only when all conditions hold:

- protocol is TCP or UDP;
- local or remote port is 53;
- the normalized flow contains at least one DNS query.

All other flows in the host group are service flows for presentation purposes.

This classification never rewrites the canonical flow object.

## Host summary policy

When service flows exist:

- owner/confidence comes from service flows;
- service remote IP/ports exclude resolver endpoints;
- DNS resolver IPs are displayed separately;
- traffic and packet totals still cover every flow in the host group;
- Timeline action links still cover every correlated flow.

When only DNS-resolution flows exist, the UI explicitly states that no service flow carrying that hostname was confirmed.

## Non-goals

v0.14 does not infer DNS answer-to-IP ownership, decrypt TLS, modify PCAP, alter package attribution, change Timeline correlation, or change Android runtime/startup behavior.
