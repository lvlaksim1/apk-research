# apk-research v0.24 — Unified Session Evidence

## Purpose

v0.24 joins the already-captured evidence into one investigator navigation model. It does not introduce a second source of truth and does not strengthen existing attribution or temporal relations.

The primary navigation chain is:

`screen ↔ action ↔ normalized flow ↔ packet ↔ process/socket ↔ raw evidence`

## Session Evidence view

The desktop application adds a `Session Evidence` tab built from the existing archived Research Timeline, normalized network-flow inventory, socket attribution and screen provenance.

Each chronological row may contain:
- target/host time;
- event type/name;
- `action_id`;
- canonical `flow_id` references;
- packet count for linked flows;
- process/PID/socket attribution summary;
- nearest Continuous Screen packet/frame locator;
- matching high-resolution `screenrecord` chunk locator when the target time is covered;
- relation type, strength and explicit causal-claim flag.

Search covers event/action/flow identities, process/PID/inode evidence, endpoints and protocol names.

## Cross-navigation

v0.24 adds direct navigation paths:
- Session Evidence → Timeline;
- Session Evidence → Evidence Explorer;
- Session Evidence → Packet Inspector;
- Packet → Evidence flow;
- Packet → screen moment;
- Timeline event → screen moment;
- Evidence node → Session Evidence / screen moment;
- Process/Socket → all flows carrying that existing attribution.

Raw packet drill-down still resolves to the original `01_raw/network/traffic.pcap`.

## Screen timing model

Continuous Screen stores Android MediaCodec `presentationTimeUs` in the device elapsed-time domain. v0.24 does not pretend that PTS is UTC on its own.

For screen navigation, apk-research uses the `realtime_to_elapsed_offset_ns` already exported from Android `screenrecord` Winscope frame timing:

`frame_target_unix_ns = continuous_pts_us * 1000 + realtime_to_elapsed_offset_ns`

When this transform is present, the navigation mapping is labeled `HIGH`. A legacy archive without it may use the separately recorded target-start boundary as an explicit estimated fallback.

The locator also reports whether the same target time is covered by a high-resolution screenrecord chunk. A chunk-rollover gap is reported as a gap rather than silently interpolated.

## Dual-source screen role

Owner-side v0.23.1 validation established the current product role:
- Continuous Screen is the stable continuous/timeline source and covers screenrecord rollover gaps;
- Android `screenrecord` remains the high-resolution 1080×1920 source;
- Continuous Screen currently remains 540×960 / 2 Mbit/s;
- sole-source replacement requires a separate future quality uplift and revalidation.

`continuous-screen.json` schema 0.2 records `experimental=false` and `evidence_role=stable-continuous-timeline`. The legacy failure status string `failed-experimental` is retained only for compatibility with older readers.

## Evidence semantics

The following boundaries are mandatory:

- RAW PCAP remains authoritative network evidence.
- Normalized flow identity remains the existing canonical bidirectional 5-tuple.
- Flow ↔ process/socket retains the attribution confidence already present in evidence; reverse indexing never upgrades it.
- Action ↔ Flow remains `temporal-only` with `causal_claim=false`.
- Packet ↔ Action remains bounded by the archived action window and same `flow_id`.
- Screen ↔ event/packet is `time-aligned-navigation`, not causality.
- No missing packet, frame or application message is synthesized.
- Encrypted traffic is not represented as decoded plaintext.

## Runtime boundary

v0.24 does not change:
- hidden Emulator → gRPC/MMAP → AndroidView live display;
- persistent geometry-safe gRPC input;
- v0.10.5 startup/clean-launch sequencing;
- raw network collector;
- canonical flow attribution rules.

Audio Evidence and user-facing Virtual Display remain out of scope.
